# RR-13 — DoS & Resource-Exhaustion Surface

**Audit:** Release Readiness (40-agent) · Wave 2 · Mission RR-13 · 2026-09-12
**Mode:** READ-ONLY. You may run short read-only benchmarks; no repo writes. All numbers measured against this repo (in-memory runs only): lobby room floor **21.7 KB/room**, started 4-seat state **15.9 KB/viewer**, 5000-event telemetry file **2.08 MB**, Socket.IO socket **~22.6 KB heap** (measured, 300 raw ws clients), `accounts.json` 416 KB / `social.json` 440 KB, scrypt login **39 ms**, per-viewer summary build+stringify **0.09 ms**.

## Findings

1. [BLOCKER] `server/serverSocketAccount.js:250` — `create-room` only leaves the prior room when the **same clientId** is supplied; omitting/rotating `clientId` (guest, no auth) leaves the old room with `disconnected=false` forever. `hasConnectedHumans` (`rooms.js:431`) then reports it live, so GC (`socketRuntime.js:707`) never reaps it and `disconnect` only cleans the newest `socketRoom` mapping. Worst case: limiter allows 24 create-room/s/socket × 21.7 KB = **~520 KB/s per socket → 2 GB heap in ~65 min (single) / ~7 min (10 sockets)**; rooms are unbounded and every lookup becomes O(rooms). Fix: key abandonment on socket (not clientId), mark host disconnected on room switch, hard per-socket/global room cap.
2. [BLOCKER] `server/telemetryModule.js:85` — every telemetry `record()` rewrites + fsyncs the whole store (`storeIO.js:56`); per settlement `recordLoggedTelemetry` (≤200) + `recordBotTelemetry` (≤200) + 32 achievement records = **up to 432 full-file writes**. At the 5 000-event cap: 432 × 2.08 MB ≈ **898 MB stringified + 432 fsyncs ≈ 4–5 s of blocked event loop per match**, repeatable every eligible match (human + bots). Fix: buffer in memory, append-only NDJSON or ≥5 s debounced flush, single write per settlement.
3. [MAJOR] `server/socketRuntime.js:185` (+ `serverSocketSocial.js:78,176`) — `candidates.forEach(recordVerifiedAchievement)` re-persists accounts (416 KB), notifications (`socialStore.js:261`, 440 KB) and achievements **per unlock**; up to 48 rules × 8 seats = 384 first-unlocks → **~330 MB + ~700 fsyncs per settlement**, each notification also rewriting 440 KB. Fix: batch all settlement writes into one persist per store; cap candidates.
4. [MAJOR] `server/serverSocketSocial.js:177` — `get-leaderboard-snapshot` is **pre-auth/unrated** and recomputes 15 leaderboards over all accounts (`accountStore.js:793`). Measured 4–5 ms @339 accounts; scales linearly → **~120–150 ms @10k accounts, 24 calls/s/socket (limiter) ≈ 3 CPU cores from one socket**. Fix: require sign-in or per-IP limit, 30–60 s cached snapshot.
5. [MAJOR] `server/socketRuntime.js:206` — `broadcastRoomState` iterates **every socket in the process** per emit (plus rejected verbs still emit, `socketHandlerSupport.js:81`). 1 000 started bot rooms at ~1.5 emits/s × 4 000 sockets ≈ **6 M membership checks/s and 1 500 × 4 × 15.9 KB ≈ 95 MB/s serialization**. Fix: `io.to(roomCode)` room fan-out; viewer-scoped second pass only when privacy differs; cache summaries.
6. [MAJOR] `server/roomSettings.js:490` — generic string settings (`bankruptMode`, `bankLoanSeverity`) are stored with only `.trim()` (up to `maxHttpBufferSize` 100 KB) and echoed in every summary (`rooms.js:556`) to every viewer. **100 KB × 4 viewers × 1.5 emits/s ≈ 600 KB/s per room**, and amplifies finding 1's per-room memory 5×. Fix: cap generic strings to 32 chars, reject unknown keys.
7. [MAJOR] `server/socketHandlerSupport.js:105` — the only rate limiter runs inside **registered** handlers; unknown/malformed events are parsed and dropped with no budget, and `server.js:58` sets no `allowRequest`/max clients. A WS peer can stream 100 KB frames at line rate (~125 MB/s on 1 Gbps) of pure `JSON.parse` CPU; connection count is unbounded. Fix: per-connection message/byte budget in `io.use`/`onAny`, max-clients + per-IP handshake throttle.
8. [MAJOR] `server/rooms.js:779` — `getRoomByPublicId`, `findLiveRoomFor`, `findRoomFor`, `getRoomByClient`, `restoreAccountSeat`, `listPublicRooms` are all linear; ghost rooms (finding 1) make a single reconnect/`list-rooms`/750 ms directory push O(100k rooms) → **2.4 M room checks/s per socket during reconnect storms**. Fix: socketId/clientId/publicId indexes; don't rely on scans.
9. [MAJOR] `server/socketRuntime.js:408,499` — each started bot room re-arms a 650 ms/450 ms timer plus a full state emit forever; no cap on concurrent started rooms. 1 000 bot rooms ≈ **1 500–2 200 timer callbacks/s + ~95 MB/s projections**; abandoned rooms keep playing up to the 10 min GC grace. Fix: max rooms/process, bot cadence ≥2 s (or pause) when no connected human.
10. [MAJOR] `server/gameLogic.js:190` — `economyTransactions` (and `contractTransactions`, :171) cache never pruned inside a game; measured cached casino result **1.2 KB** each. One socket sustaining 24 $1 spins/s grows **~18 MB/10 min, 66–108 MB/hour/room** (cash-limited but bankruptcy-prone attacker can rotate rooms). Fix: fixed-size LRU or prune by round/age.
11. [MINOR] `server/accountStore.js:494` — `sessions`/`sessionHashes` grow per login and are persisted; each login also rewrites 416 KB and blocks 39 ms in scrypt. 8/min/IP → **480 stale token pairs/h/account + ~200 MB/h rewrite**. Fix: TTL/LRU cap, keep hashes in memory (prior 8.8).
12. [MINOR] `server/server.js:50,69` — HTTP limiter is **disabled by default** (`max=0`), and `express.static` accepts ranges on the 11.74 MB mp3 (plus a 3.19 MB extensionless `assets/fonts/test`). One full-file worth of **1-byte range requests (11.7 M max)** forces one open/read per request with no 429. Fix: enable HTTP limit by default, `immutable` cache headers, cap/deny ranges or front with CDN.
13. [MINOR] `server/rooms.js:818` — `leaveRoomByClient` deletes the registry entry directly, bypassing `destroyRoom`; auction/turn/bot timer maps keep roomCode keys and closures keep the room alive, and bot timers can re-arm because `room.destroyed` is never set (prior 8.6 still open). Fix: funnel all removals through `destroyRoom`.
14. [MINOR] `server/socialStore.js:261` — every notification/mark-read rewrites the entire 440 KB social file; season (`seasonModule.js:335,364`, standings up to 5 000 entries) and cosmetics (`cosmeticCatalog.js:122`) likewise rewrite whole stores per action. Worst simple path: friend request = 2 full social rewrites + 440 KB notification write. Fix: dirty-flag + debounced single write.
15. [MINOR] `server/server.js:133` — no health/readiness endpoint (SPA fallback returns 200 for any GET, `server.js:70`), no load shedding or backpressure; under heap/event-loop pressure pings time out → mass disconnect → O(rooms) restore (finding 8), and any uncaught error exits the process, dropping all in-memory rooms. Fix: `/healthz`+`/readyz`, handshake rejection budget, staged load-shed (stop new rooms/bots first), SIGTERM drain.

## Safe operating envelope (launch)

- **Connections:** ≤ 800–1 000 sockets per process (default FD soft limit 1024 binds before heap; 22.6 KB each ≈ 23 MB + buffers), max 5–10 per IP, handshake throttle 10/min/IP, `max-clients` set explicitly.
- **Rooms:** ≤ 150–250 concurrent rooms/process (≈ 5–10 MB) — of which ≤ 25 started bot rooms; 1 room per socket enforced server-side; reject create-room over budget.
- **Payloads:** keep `maxHttpBufferSize` 100 KB but enforce ≤ 16 KB per application event; chat 250 chars / 500 ms cooldown; generic setting strings ≤ 32 chars; unknown events counted against the same 240/10 s budget (or dropped pre-parse).
- **Rates:** HTTP limiter ON by default (600 req/min/IP), 10 new sockets/min/IP, 24 game events/10 s (current); bot cadence ≥ 2 s when no human is connected.
- **Disk:** one persist per store per settlement; telemetry batched/append-only (≥ 5 s debounce); never fsync on a user-action path; backup off-thread (prior 8.5).
- **Headroom rule:** alert at 60% of room/socket budgets and 70% heap; at breach, stop room creation and bot decisions first — do not wait for fsync/queue stalls, since those cascade into ping-timeout reconnect storms.
