# RR-24 — Network Failure & Reconnect UX

**Audit:** Release Readiness (40-agent) · Wave 3 · Mission RR-24 · 2026-09-12
**Mode:** READ-ONLY.

Verified current state of prior findings: R2 §4.8 (actions enabled while RECONNECTING) is **still current** (`main.js:282-293`); R3 §1.2 (session wipe on any auth failure) is **still current** (`clientSocketListeners.js:52-61`); server-restart handling is unchanged from the "silent restart loss" finding (`server.js:129-139`, audit 8.1). Deeper UX findings below.

## Findings (14)

- **[BLOCKER] server/socketRuntime.js:261-271** — Scenario 6 (host disconnect) — `reassignHostIfNeeded` picks the first non-disconnected player **including bots**, emits no message, and never re-elects on host reconnect (`rooms.js:735-750`); a human who reconnects after a bot became host finds Start permanently disabled with zero explanation, and the room never GCs while they wait. — Exclude bots/prefer humans, emit "`X` disconnected — `Y` is now host", and re-elect (or return the host role) when the original host reconnects.
- **[MAJOR] clientGameSave.js:85-115 + server/server.js:129-139** — Scenario 2 (server restart) — Restore failure leaves the player on the frozen board: only a `CONNECTION / No active session found.` toast and OFFLINE status; no redirect, no "table closed" messaging, controls stay enabled and emit into a dead room; the confirm-modal escape (`clientLobbyUi.js:891-898`) still claims "Leaving now releases your seat… assets stay on the table". — On failed restore mid-room, show a blocking "This table closed (server restarted)" surface with a Return Home action and clear the save automatically.
- **[MAJOR] clientSocketListeners.js:46-50,247 + main.js:405-425** — Scenarios 1/2/12 (honesty) — On every connect the client announces "Live table connection restored." **before** the restore ack, then flips to "Table connection offline." when the ack fails even though the socket is healthy; `setConnectionStatus("offline")` is sticky (no code path restores online without a snapshot), and `clientRoomsUi.js:290` then refuses directory auto-refresh. — Announce only after successful restore; separate "session gone" from "connection down"; re-assert online from any successful server response.
- **[MAJOR] public/index.html:556 + public/styles.css:554,1040 + clientTopNavRender.js:63-66** — Scenarios 1/7/8 (visible state) — In game there is **no visible connection indicator at all**: `#tn-online` is `.sr-live` (1px clip), `#tn-connection-note` doesn't exist, and `#view-game .pr-right` hides the AFK/online seat chips; only a transient chat line signals outage. — Add a visible reconnecting/offline pill/banner to the game chrome and restore per-seat online chips.
- **[MAJOR] main.js:282-293,577-630 + clientHudRender.js:98-130** — Scenarios 1/7 (slow acks) — Roll, End Turn, chat, BUY, auction bid, and trade actions stay enabled while RECONNECTING; socket.io buffers emits, the 8s guard says "Roll could not be confirmed — try again.", and the buffered action can still execute after the failure message, inviting double actions. — Gate mutating game actions on `connectionStatus`, or queue them visibly as pending and reconcile after restore.
- **[MAJOR] clientGameModalsUi.js:141-157** — Scenario 5 (trade modal) — Accept disables both buttons with **no timeout**; a lost ack leaves PROCESSING… forever; when the offer was cancelled during a disconnect, the failure branch re-adds the stale offer and reopens the modal, so Accept repeatedly yields "No matching trade offer was found." with no expiration explanation. — Use `emitWithTimeout`, close the modal when the snapshot clears `pendingTrade`, surface "This offer expired while you were away."
- **[MAJOR] clientTradeUi.js:929-945,1080-1094 + clientStateSync.js:155-161** — Scenario 5 (contract negotiation) — Disconnect cancels `pendingPlayerContract` server-side (system-message only, `socketRuntime.js:653-670`); on return the snapshot nulls the offer but `#financing-modal` is never re-rendered or closed — SEND COUNTER silently returns (`clientTradeUi.js:931`) and the modal looks live but is dead. — Snapshot-driven close/replace of the negotiate view plus a "contract canceled while you were away" notice.
- **[MAJOR] server/socketRuntime.js:653-670,638-646** — Scenarios 3/4/5 (missed explanations) — Trade/contract cancellations and "highest bidder disconnected, bid reset" are `system-message` broadcasts only, so the away player never sees why their deal vanished or bid reset; unlike turn-skip (`gameLogic.js:1091`) they aren't in the snapshot-replayed feed. — `feedMessage` these events and summarize "while you were away" changes on restore.
- **[MAJOR] server/socketRuntime.js:610-630 + clientStateSync.js:155-161,262** — Scenario 3 (long disconnect) — On return after >10s grace the only feedback is "Reconnected to your room."; the disconnect broadcast and "was skipped due to disconnect" exist only in the LOG drawer, which isn't auto-opened; no toast/status tells the player their turn was skipped. — Restore-time recap: "You were offline ~Ns — your turn was skipped; feed since then: …".
- **[MAJOR] server/auctionApi.js:149-155,169-181 + socketRuntime.js:638-646** — Scenario 4 (mid-auction disconnect) — The countdown keeps running (by design; snapshot reopens the modal correctly at `clientStateSync.js:322-328`), but a leading bidder dropped at t=0 can still win and **be charged at the 5s close** (disconnected flag only flips at the 10s grace), or have the bid reset at 10s; only feed lines explain, reset is system-message only. — Include the reset in feed and show an explicit "auction closed while you were away — you won/paid/cancelled" recap; consider pausing/extending on expiry.
- **[MAJOR] clientSocketListeners.js:52-61** — Scenarios 1/2 (identity loss) — R3 §1.2 still current: any non-success `account-restore` ack (transient rate-limit/server error during a reconnect storm) calls `saveAccountSession(null)`, silently logging the player out to guest mid-outage. — Clear the stored session only on explicit invalid/expired-token errors.
- **[MAJOR] server/rooms.js:735-750** — Scenario 9 (multi-tab) — `restoreConnection` overwrites `player.socketId` for a **live** seat when the clientId matches (duplicated tab copies sessionStorage); no liveness guard and no takeover message — the original tab keeps rendering but every action fails with generic errors. — Reject restore when the old socket is live, or notify both tabs ("Session moved to another tab") and demote the old one.
- **[MINOR] clientLobbyUi.js:701-731,890-902** — Scenarios 8/11 (copy/recovery) — While offline, quick-table directory timeout declares "NO OPEN TABLES — HOSTING A NEW PUBLIC TABLE." and then fails 12s later with "Room entry timed out"; mid-dead-room leave still uses the forfeit-a-live-round confirm copy. — Make timeout copy offline-aware ("You appear offline — retrying") and check room liveness before offering "forfeit".
- **[MINOR] clientSocketListeners.js:245 (absence) + clientGameSave.js:104-115** — Scenarios 8/10/11 (proactive detection & backgrounding) — No `navigator.onLine`, `online`/`offline`, `visibilitychange` (for the game socket), or `pageshow` handling anywhere (only Night Shift/casino/theme); mobile/bfcache return can sit on a stale board until the next socket event, and home keeps advertising "Resume round / SAVE FOUND" for a dead save. — Add online/offline + visible/pageshow resync (re-emit restore-session, refresh feed/economy) and validate the save before showing Resume.
